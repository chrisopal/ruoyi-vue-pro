# TIC LIMS Report Output Minimum Design

Date: 2026-06-14
Branch: `feature/tic-lims-report-output`

## 1. Purpose

The current report center already treats report templates and `ReportDraftPlan` as governed configuration assets. The remaining drift is that LIMS can create a report record, but the requested output formats still stop at configuration and do not become report artifacts.

This design closes the minimum execution loop:

```text
Frozen WorkflowSnapshot
  -> ReportDraftPlan
  -> report content/data snapshot
  -> WORD/PDF/EXCEL output artifacts
  -> report_output JSON
  -> issued report evidence object
```

## 2. Scope

In scope:

1. Add `report_output` to `lims_report` as the governed output manifest.
2. Generate real minimum files for configured output formats:
   - Word compatible `.docx`
   - PDF compatible `.pdf`
   - Excel compatible `.xlsx`
3. Keep `file_url` as the primary signed/issued artifact URL for evidence-chain compatibility.
4. Drive formats from the frozen `ReportDraftPlan.outputFormats`, not ad hoc request input.
5. Expose output artifacts in the LIMS report admin page.
6. Cover the flow with focused unit tests.

Out of scope:

- Rich visual report layout designer.
- Complex pagination, headers, seals, signatures, or regulatory page stamping.
- Object storage integration and presigned download URLs.
- AI-generated narrative text.

## 3. Domain Boundaries

### 3.1 LIMS Report Execution Context

LIMS owns report execution and output generation because outputs are produced from request, task, result, and snapshot data.

New service:

```text
ReportOutputGenerator
  input: report metadata, report content JSON, ReportDraftPlan
  output: ReportOutputBundle
```

`LimsWorkflowService` remains the application orchestrator. It should not know file format internals.

### 3.2 Storage Boundary

The first slice writes deterministic local artifacts under `target/lims-report-output`. This is an implementation adapter boundary, not a domain rule.

Future replacement:

```text
ReportOutputGenerator
  -> ReportArtifactStorage
  -> Infra File API / object storage
```

This batch intentionally avoids coupling LIMS report generation to Infra file configuration before the report artifact contract is stable.

## 4. Data Contract

`lims_report.report_output` stores JSON:

```json
{
  "primaryFormat": "PDF",
  "primaryFileUrl": "/lims/report-output/RPT-REQ-001/RPT-REQ-001.pdf",
  "generatedAt": "2026-06-14 18:30:00",
  "outputs": [
    {
      "format": "PDF",
      "fileName": "RPT-REQ-001.pdf",
      "fileUrl": "/lims/report-output/RPT-REQ-001/RPT-REQ-001.pdf",
      "contentHash": "sha256...",
      "generatedAt": "2026-06-14 18:30:00"
    }
  ]
}
```

Rules:

- `PDF` is the preferred primary format when present.
- Otherwise use the first generated artifact.
- `file_url` mirrors `primaryFileUrl`.
- `contentHash` is calculated from the actual generated bytes.
- The manifest belongs to the report record and is included in admin responses.

## 5. Execution Flow

```text
generateReport(requestId)
  1. Load request and frozen workflow snapshot.
  2. Build report content from request, tasks, equipment evidence, results, and result values.
  3. Build ReportDraftPlan from the same frozen snapshot.
  4. Generate configured output artifacts.
  5. Insert lims_report with report_content, data_snapshot, hashes, report_output, and file_url.
```

Issue flow remains:

```text
issueReport(reportId)
  -> mark issued
  -> register EvidenceObject(REPORT) using file_url and data_snapshot_hash
  -> link evidence to request/report clause context
```

## 6. Acceptance Criteria

1. `generateReport` stores `report_output` with configured WORD/PDF/EXCEL artifacts when the frozen report draft plan requests them.
2. `file_url` points to the primary artifact and still feeds report evidence.
3. Report admin page displays the output manifest.
4. Unit tests prove the manifest, output hashes, and primary PDF selection.
5. Maven targeted tests pass.
6. Server compile passes.
7. Frontend build or focused type check passes.

## 7. Risks

- Local file output is not a production storage strategy. It is intentionally a replaceable adapter until object storage/signature requirements are finalized.
- The generated files are minimum valid artifacts, not final regulatory report layouts.
- Existing databases need an incremental migration for `lims_report.report_output`; `lab.sql` only defines the bootstrap schema.
